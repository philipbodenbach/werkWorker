## Token comparison

Both schemas call `CreateRestrictedToken` with `DISABLE_MAX_PRIVILEGE | LUA_TOKEN | WRITE_RESTRICTED` (`0x0d`). Schema 4 includes the account and Everyone among the restricting principals. Schema 5 has one private writer, excludes it from ordinary groups and disables inherited logon groups. Its suspended payload must have the expected account and package, no capabilities, Low integrity, no elevation and only the enabled traversal privilege. The runner checks the final primary token before resume. Its own storage verifier briefly impersonates the payload to inspect pinned resources and reverts. The records do not identify a thread impersonation token at the exact Rust loader call. [Runner](../src/runtime/windows_tree_runner.rs) · [Storage verifier](../src/runtime/windows_appcontainer_storage.rs)

On this system bcrypt requests `SYNCHRONIZE | FILE_READ_DATA | FILE_WRITE_DATA` (`0x00100003`) by name on `\Device\KsecDD`. The device grants read and write to several broad principals, read to Restricted Code, and has a Low no-write-up label. Its DACL contains neither the private writer nor the per-logon SID. With the sole writer, `0x00100001` succeeds and the requested additional write bit is denied. A private-writer ACE on an **in-memory copy** of the descriptor explains the difference. The live device descriptor was never changed. [Measured descriptor, requested mask and DLL identity](evidence/windows-process-tree-2026-11-18/bcrypt-write-check.json)

| Candidate | Decision and scope |
| --- | --- |
| Private writer, full restriction in place of write-only restriction | Both fixed diagnostic images had already stopped before their entry markers. Restoring the write-only variant returns to the measured device denial. |
| Add a logon or another private SID | There is no matching device write ACE for either proposed identity. Using Everyone to satisfy the write check also admits that trustee on other objects. A restricting SID identifies a principal across securable objects. |

## Focused native experiments

**Integrity as an independent write boundary.** The hypothesis was that an Untrusted token could block Low-integrity file writes while retaining the right needed for the Low-labelled device. Such a design would have to admit the same write bit at the device without the exclusive writer. Before constructing a broader payload, the experiment tested that necessary condition. Its only token change was lowering the integrity of a copy of the ordinary tester's token. Windows applied the effective thread token to real, named `OPEN_EXISTING` requests on newly created, private NTFS files. Both had the same discretionary grants for the tester and SYSTEM. The program verified NTFS, the two explicit grants on each protected DACL, each mandatory label and the effective token after impersonation. This isolates mandatory integrity from the AppContainer and its discretionary checks. [Diagnostic source](../tests/diagnostics/windows_mandatory_file.py) · [Microsoft mandatory integrity model](https://learn.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control)

| Effective integrity | Target label | Read and synchronize | Read, write and synchronize |
| --- | --- | --- | --- |
| Low | Low / no-write-up | Opened | Opened |
| Untrusted | Low / no-write-up | Opened | Access denied (5) |
| Untrusted | Untrusted / no-write-up | Opened | Opened |

The positive control rules out a blanket failure to open a file with the larger mask. The device and an ordinary Low file share the relevant mandatory label. Lowering integrity supplies no way to distinguish them. Remaining at Low leaves discretionary grants relevant for other Low objects. This is a file-handle result. It establishes neither a device open under the Untrusted token nor a file or Registry write from a payload. The read/write handles were closed without writing. The test reverted impersonation, removed both files and their directory and drained its outer Job. To repeat just this control, run `python -B tests/diagnostics/windows_mandatory_file.py` in an ordinary Medium PowerShell from the repository root.

**Passive inheritance of a broker-opened device handle.** The last genuine uncertainty was whether system bcrypt would use a handle already present at process attach. The two arms used the same trusted fixed image, the same fresh test package, a private sole writer, `0x0d` token flags, Low integrity, zero capabilities and a bounded Job. A read-only handle for the fixture image was the control. The other arm received one read-only KsecDD handle. This additional handle was the candidate's only intended new authority. The root used the ordinary test account for this diagnostic. The production dedicated account, private Desktop and the full tree were outside its scope.

Both images reached entry, verified the inherited handle's object name and observed effective rights `0x00100081` (including read attributes, without write data). The probe saw no impersonation token on its own thread immediately before the load sequence. System `sechost.dll` loaded in both arms, bcrypt was initially absent, and loading system bcrypt returned 1114 in both arms. Each Job accounted for one member and finished at zero. The two arms shared a temporary per-user profile whose registration and directory were absent before creation and after deletion. The observed device owner/DACL and mandatory label matched before and after. The earlier DACL serialization listed the same six allow grants in a different order. No device ACL or namespace permission change was required.

This rejects passive inheritance of **this read-only handle** on this build. The measured bcrypt image opens the device by name. A library needs a contract to consume an inherited handle in place of its own open. Reusing existing scoped IPC for ordinary broker operations does not route loader I/O through the broker. Supplying a stronger handle would add authority and still require a supported runtime consumer and a bounded way to propagate it. ## Boundary required for integration

Retain the suspended launch, verified token, private desktop, host-owned Job and three-handle stdio allowlist. A host-job solution needs an OS policy that distinguishes authorized file and Registry **objects and operations** from the device open. It must be active before the first payload instruction and apply to every descendant, relevant impersonation, writable mapping and transferred handle. The broker must still verify the final object after path resolution and limit the authority of handles it supplies. Ordinary device admission must leave toolchain writes, package-profile writes, broader Registry writes and host-file modifications denied.

| Additional mechanism | Compatibility and outstanding proof |
| --- | --- |
| Packaged Win32 app isolation | Requires a supported Windows build and suitable packaging. Its documented AppContainer, capabilities and virtualization deserve evaluation against the exact host scope. There is no demonstrated per-object repair here for this unchanged Cargo and runner. [Windows requirements and model](https://learn.microsoft.com/en-us/windows/win32/secauthz/app-isolation-overview) |
| PSEC and MXC | The prior PSEC experiment observed absent atomic membership in the required Job and three members at cap two. The alternative MXC IsolationSession backend requires a newer Windows build. A new backend must preserve authenticated launch, pipe handling, strict Job limits and cleanup. [Local measurements](windows-process-tree-qualification.md) · [MXC release requirements](https://github.com/microsoft/mxc/releases/tag/v0.9.0) |
| Independent filesystem and Registry enforcement | A supported, managed native enforcement layer would have to identify the dedicated sandbox before resume and cover both object classes. Signing, installation, update, recovery, inherited handles, writable sections, aliases, permission changes and descendants are part of its acceptance burden. A filesystem filter alone leaves Registry operations uncovered. Driver implementation is outside this task. [Filesystem filters](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/about-file-system-filter-drivers) · [Registry filtering](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/filtering-registry-calls) |
| VM-backed execution | A separate Windows kernel can provide guest-local crypto and Registry objects. Workspace transfers, networking, supervision and resource budgets would need qualification across the guest boundary. This changes the execution location from the requested native host Job. [Microsoft isolation modes](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/hyperv-container) |

The next native decision is to identify an available, supported enforcement layer with a documented guarantee for both file and Registry writes. Require object-identity, handle and three-generation tests on private fixtures before widening the token. Only a passing candidate advances to Rust entry, installed Cargo and the complete release suite, including DNS and both console cases. Existing protocol and provider results remain attributable to the reidentified binaries.
