# Native Windows PSEC evaluation for PR #24

**Outcome B. Keep `sandbox_unqualified` on Windows 11 build 26200.9974.** The native API accepted the policy and the fixed write probe completed. The original Rust probe timed out, the required Registry write boundary remains unproven, and a prior measurement of this native launch contract recorded three live Job members at limit two. ## Observations on the test host

| Control | Result |
| --- | --- |
| Runtime support | The x64, non-elevated Medium host queried the signed System32 `processmodel.dll`. Both runtime calls returned `S_OK`. PSEC version 1.1 is available. Mask `0xF` reports filesystem deny, network proxy, filesystem enumerate and network ingress. |
| Authorized writes | A fixed probe created fresh files in the private workspace and private temp and printed `PRIVATE_WRITES_OK`. It exited with code 0 in 16 ms. The host verified the exact bytes and SHA-256 of both files. |
| Runtime initialization | The original `probe.exe --list` had the same SHA-256 as the prior eight-test control. Its root resumed with stdin at EOF and its output pipe drained during the wait. After 30,032 ms Windows reported `WAIT_TIMEOUT` and `STILL_ACTIVE`, with zero output bytes. Entry into the Rust test harness and the cause of the timeout are unconfirmed. |
| Actual tokens | Before resume, both roots were non-elevated Low AppContainers. Each had one effective capability SID and zero restricting SIDs. Win32k denial was active. The LPAC query returned Win32 error 87, leaving LPAC status unknown. |
| Low-integrity permission fixtures | Windows `AccessCheck` on the real tokens granted `KEY_SET_VALUE` for broad direct and effective inherited permissions. The read-only control denied the right. A separate, always-suspended root with the same policy and image produced the same three decisions for `FILE_WRITE_DATA`. |
| Cleanup | The write probe and timed-out Rust probe both had signaled process handles and zero active members after cleanup. The separately inspected file-fixture process was reaped while still suspended. The enclosing Jobs also drained. |

The Low fixtures from the preceding assessment were synthetic security descriptors. The current checks exercised those discretionary permissions in memory. The only new persistent writes verified here were the two authorized files. Actual mutation or virtualization of a host Registry key, and the outcome of a live file open outside the allowed directories under this exact policy, remain unmeasured. ## Native enforcement contract

The audited Microsoft MXC revision is `51805f40beaf19631df63ae25d0c11876d05a4ce`. The diagnostic explicitly used `CreateProcessSecurityEnvironment`, attached `PROC_THREAD_ATTRIBUTE_SECURITY_ENVIRONMENT` at `CreateProcessW`, and observed successful creation of the environment and suspended roots. It used the existing policy encoder. Its 12 generated schema files matched the Microsoft revision after line-ending normalization. The launch ran directly against the OS without SDK backend selection or fallback. [Microsoft support table](https://github.com/microsoft/mxc/blob/51805f40beaf19631df63ae25d0c11876d05a4ce/docs/backends/process-container/os-version-support.md) · [Native API flags](https://learn.microsoft.com/en-us/windows/win32/api/processmodel/ne-processmodel-process_security_environment_support_flags)

**Filesystem.** The submitted FlatBuffer requested read/write access for the two fixture directories, read-only access for the fixture runtime and System32, and denies for the C: and F: volume roots. It specified Win32k denial, UI mask `0x3ff`, zero explicit capabilities and default-deny network rules. Microsoft documents ambient AppContainer grants, equal-path deny precedence, and narrower explicit writable grants under a parent deny. Its volume-root exception is documented for grants. The measured permission checks do not exercise the PSEC filesystem filter. The earlier same-build test did observe an explicit image deny take effect. Coverage across file identities, alternate paths, mounted volumes and previously granted handles remains a prerequisite for an exclusive write scope. [Microsoft filesystem model](https://github.com/microsoft/mxc/blob/51805f40beaf19631df63ae25d0c11876d05a4ce/docs/backends/process-container/filesystem.md) · [Path precedence](https://github.com/microsoft/mxc/blob/51805f40beaf19631df63ae25d0c11876d05a4ce/docs/schema.md#L450-L521) · [Measured image deny](evidence/windows-process-tree-2026-11-14/psec-native.log)

**Registry.** The pinned PSEC schema and mapper expose neither a host-key write scope nor a selectable private hive. BaseContainer rejects a request for LPAC. Microsoft's Registry control reads a host value with an explicit `registryRead` capability. The WerkWorker requirement is an inherited write boundary, including the package profile and persistent host state. The observed discretionary grants would require an additional OS enforcement or virtualization guarantee. No such guarantee was established for this PSEC tree. [Native schema](https://github.com/microsoft/mxc/blob/51805f40beaf19631df63ae25d0c11876d05a4ce/external/windows-sdk/ProcessSecurityEnvironment.fbs#L41-L54) · [Policy mapper](https://github.com/microsoft/mxc/blob/51805f40beaf19631df63ae25d0c11876d05a4ce/src/mxc-sdk/src/backends/process_container/common/base_container_helpers.rs#L30-L65) · [Microsoft Registry test](https://github.com/microsoft/mxc/blob/51805f40beaf19631df63ae25d0c11876d05a4ce/tests/scripts/run_processcontainer_contract_tests.ps1#L198-L205) · [AppContainer virtualization](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-for-legacy-applications-)

**Startup, descendants and handles.** The native environment is attached at process creation. In pipe mode the pinned runner explicitly lists its standard handles and verifies Job setup before resuming the root. The diagnostic verified membership of both suspended roots. This establishes the timing of the initial setup. Enforcement on descendants, on authority already conveyed through handles, and on operations mediated by another service needs an independent guarantee. The WerkWorker broker can authorize the requests that enter its own interface. [Pinned launcher](https://github.com/microsoft/mxc/blob/51805f40beaf19631df63ae25d0c11876d05a4ce/src/mxc-sdk/src/backends/process_container/common/base_container_runner.rs#L843-L905) · [Job setup](https://github.com/microsoft/mxc/blob/51805f40beaf19631df63ae25d0c11876d05a4ce/src/mxc-sdk/src/backends/process_container/common/base_container_runner.rs#L982-L1049)

**Hard Job limit.** The November 14 native test on this OS build used the same API sequence. In the atomic-assignment arm, the suspended PSEC root was outside the requested Job and was reaped before resume. In two separate console-child runs the root was explicitly assigned before first resume. A census of each concrete Job found the root, its child and `conhost.exe` simultaneously alive at limit two. Both observations concern console-child startup. The six historical Jobs were cleaned up. That run recorded the OS build without a hash of its OS DLL. ## Integration decision

This host-Job design requires a Windows enforcement point that bounds persistent Registry writes for the entire process tree, or a private Registry with demonstrated isolation from host state. It also needs a hard admission limit that includes system-created console helpers. A new protocol field alone cannot supply either property. [Microsoft OS feature guide](https://github.com/microsoft/mxc/blob/51805f40beaf19631df63ae25d0c11876d05a4ce/docs/development/guides/process-container-adding-os-features.md#L25-L74)

Gate 3, Cargo and the installed-package suite were withheld after the focused checks. The tested Worker branch was `feat/windows-child-process` at `87a999a`. All 139 original product inputs, the package and its four installed executables were rehashed against the earlier acceptance. The earlier installed run stopped at admission. Historical restoration for `111dd` remains unconfirmed.
